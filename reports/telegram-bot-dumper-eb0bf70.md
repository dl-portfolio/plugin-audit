# soxoj/telegram-bot-dumper — USE WITH PRECAUTIONS
Commit `eb0bf708029aa365dc6ab79444488eb52185458b` · audited 2026-11-09 · Python CLI (`dumper.py`, Telethon) that logs in to Telegram with a **bot token** and dumps the bot's chats, media, users and profile photos to disk, plus a local web viewer (`webapp/server.py`) that browses dumps and can live-stream new messages.

**Bottom line:** No malware, telemetry, obfuscation or hidden instructions were found. The only network peer is Telegram, optionally reached through Tor. The tool does what it says. The main risk is that it is built to process **hostile content**: the docs pitch it for dumping malware C2 bots. Yet it saves every received document under the **sender-chosen filename with no sanitizing**, so a crafted name could write a file outside the dump folder. Use `--no-media` or run it in a VM/container. **The VM run did not exercise the tool at all** (Telethon was never installed and neither program was started), so this verdict rests on code review.

## What it can touch
- **Network:** Telegram MTProto servers (via Telethon) only. With `--tor`, it goes through a SOCKS5 proxy at `127.0.0.1:9050`. No other hosts are in the code. `t.me` appears only in printed text.
- **Credentials:** reads `API_ID`/`API_HASH` from the environment and takes the bot token from `--token` or a prompt. It **writes the bot token in plaintext** to `<bot_id>/bot.json` and the Telethon auth key to `<bot_id>/<bot_id>.session`.
- **Files:** creates `./<bot_id>/` (or `--output/<bot_id>/`) with history text, JSON, CSV and media. On re-run it renames the old dump to `<bot_id>_<timestamp>` (unless `--resume`). It removes only a folder it just created after an invalid token. It does not touch shell startup files, agent config, Keychain or browser data.
- **Web viewer:** `http://127.0.0.1:8010` by default (`HOST`/`PORT` env). It serves files from the dump root (default: the repo folder) after you log in with the bot's token. `--allow-new-dumps` lets the page log in to Telegram with any token you paste.
- **Processes / persistence:** none. No install hooks, Claude hooks, auto-update or background services. Listen mode runs until you press Ctrl+C.

## Runtime behaviour (VM, decoy credentials, network blocked)
- **Install:** the auto scenario ran `uv pip install -e .`. `pyproject.toml` has only a pytest section, so uv built an empty placeholder package `webapp==0.0.0`. **`requirements.txt` (Telethon, PySocks) was not installed.** Hosts contacted: `pypi.org` and `files.pythonhosted.org` (build backend only).
- **Run:** only `cat` on the planted `~/.claude/settings.json` and `~/.claude.json`. Neither `dumper.py` nor `webapp/server.py` ran.
- **Results:** 0 decoy reads, 0 refused hosts, 0 direct-egress attempts, no persistence, no leftover processes. The only new files were the two configs the scenario itself planted. These results say **nothing about the tool**, because none of its code ran.

## How to use it safely
1. **Pin the commit** (`git checkout eb0bf70`) and install in a venv: `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt`. Pin `pysocks` too.
2. **Dump untrusted bots (anything C2/malware-related) only inside a VM or a throwaway container**, never directly on your Mac. Use the local `docker compose up --build` from this commit rather than the Docker Hub image. On a bare host, add **`--no-media`** until filenames are sanitized (photos are saved under numeric IDs and are safe).
3. Treat each dump folder as a **secret**: it contains the bot token and a Telegram session. Don't commit, sync or share it. Delete `bot.json` and `*.session` before handing a dump to anyone. Use the zip export, which leaves out bot-level files.
4. Run the viewer on loopback only (the default). Leave `--allow-new-dumps`/`--allow-public` off unless you need them. Don't open `/file/...` URLs of dumped `.html`/`.svg` files in the browser.
5. Use a dedicated Telegram `API_ID`/`API_HASH`: all dumping activity is tied to that developer account. Make sure you are authorized to access the bot whose token you use.
6. Re-audit before updating.

## Not covered
- **No runtime coverage of the tool.** The auto scenario never installed `requirements.txt` and never ran the CLI or the viewer, so the Telethon install, `dumper.py --help`, the viewer startup and its HTTP endpoints, and the Docker build were all untested. Live Telegram access could not be tested anyway (network closed, no real token). A useful re-run would be: install.sh `uv venv .venv && uv pip install --python .venv/bin/python -r requirements.txt`; run.sh `timeout 60 .venv/bin/python dumper.py --help`, `timeout 60 .venv/bin/python dumper.py --token 1:x --no-listen` (expect an API_ID error, no network), `timeout 60 .venv/bin/python webapp/server.py --selftest`, and `webapp/server.py` on a sample dump folder for ~45 s.
- **Third-party code:** Telethon 1.45.0 and PySocks were not reviewed. The `soxoj/telegram-bot-dumper-web` Docker Hub image was not compared with this source.
- **Path traversal not proven end to end:** it depends on whether Telegram passes `/` or `..` in document file names. That was not tested.
- **Unread files:** `.env.example` is hidden by the reviewer's deny rules (`static/unreadable-by-reviewer.txt`). The VM scanners covered it, and gitleaks flagged nothing there. Tests and the `docs/` HTML previews were scanned by grep only. No symlinks were stripped.
- **Linux VM ≠ macOS**, and evasion by malware remains possible in general.
