# pullboard-dev/pullboard — USE WITH PRECAUTIONS
Commit `c3c21438ebda51fc410519b23cdea68801b1bb79` (v0.9.3) · audited 2026-11-09 · Node CLI (no dependencies) that sets up a "work board" for teams of coding agents. It stores the board in your repo's `.git`, adds git hooks, Claude Code / Codex hooks and skills, runs a local web view, and has an optional cloud relay at app.pullboard.dev.

**Bottom line:** No malware, phone-home, credential theft or hidden instructions were found. Every scanner CRITICAL is a false positive. The risk comes from how much it sets up. `init` permanently adds hooks that run shell commands from the repo's `pullboard.json`. `init` and `resume` start a background local web server that the website app.pullboard.dev can read and control through your browser. The skills tell agents to merge, push and release on their own. Use it only in repos you control, and turn the background view off. **The VM run only printed `--help` and `--version`**, so this verdict rests on code review.

## What it can touch
- **Repo files (`init`):** `SPEC.md`, `DOCTRINE.md`, `pullboard.json`, `AGENTS.md`, `CLAUDE.md` (`@AGENTS.md`), `.claude/skills/pullboard-*`, project `.claude/settings.json` and `.codex/hooks.json` (SessionStart/Stop/SessionEnd hooks), git hooks plus `core.hooksPath`, and an SQLite board inside `.git`.
- **Home folder:** machine settings and a project registry, relay keys as owner-only files (0600/0700). SSH key *paths* are passed to `ssh-keygen` only for spec sign-offs and relay device vouching. Node reads only `.pub` files.
- **Keychain:** only its own legacy entry `pullboard.board-key` (read, copied to a file, then deleted).
- **Processes:** git, `ssh-keygen`, the gate/check shell commands from `pullboard.json` and spec rows, and a detached background `pullboard view` server on loopback.
- **Network:** nothing by default. With the opt-in relay: `app.pullboard.dev` (GitHub sign-in, board snapshots that are encrypted on your machine) and `api.github.com/users/<login>/keys` (public keys). `pullboard intake` fetches GitHub issues and PRs. Optional SSH "runners" on hosts you configure.
- **Browser:** the local view accepts cross-origin API calls from `https://app.pullboard.dev`.

## Runtime behaviour (VM, decoy credentials, network blocked)
- **Install (auto scenario):** `npm install` with nothing to install (no dependencies). There were 0 hosts contacted and 0 DNS lookups. The one decoy read was `~/.npmrc` by npm itself, which is expected. The scenario's own `echo` created the planted `~/.claude` files.
- **Run:** `pullboard --help` and `--version` (0.9.3) worked offline. There were 0 decoy reads, 0 DNS lookups or connections, no persistence and no leftover processes.
- **What the auto scenario did not exercise:** `init` (hooks, `core.hooksPath`, CLAUDE.md/AGENTS.md, skills, project Claude settings), the background view server and its app.pullboard.dev access, `relay on` (GitHub sign-in, SSH vouch, uploads), `tour`, gate/submit/pre-push shell runs, firing the Claude/Codex hooks, `pullboard run`, `sync`, `intake` and SSH runners. The clean runtime result therefore says almost nothing about these paths.

## How to use it safely
1. Pin the version: `npm i -D pullboard@0.9.3` (or `-g pullboard@0.9.3`), not `npx pullboard` or `@latest`. Treat each upgrade as a re-audit, because it runs in hooks.
2. Turn off the background view unless you want app.pullboard.dev to reach your boards. Set `"view": { "background": false }` in pullboard's machine settings file (`init` prints the path), or `PULLBOARD_VIEW_BACKGROUND=0`. Stop a running one with the `kill <pid>` it prints. When you need the board, use `pullboard view` in a terminal and open the local link.
3. Answer **n** to the relay question at `init`, unless you want phone or multi-machine sync and accept pullboard.dev as a service provider. Undo with `pullboard relay off`.
4. Run `pullboard init` only in repos you own. Before committing in a cloned pullboard repo, read `pullboard.json` (`gate`, `check`) and the spec's check strings, because the hooks run them. Undo with `git config --unset core.hooksPath` and by removing the pullboard entries from `.claude/settings.json` and `.codex/hooks.json`.
5. Keep Claude's permission prompts on for coordinator sessions. Don't let it `land`, push or release unattended unless the repo and CI are set up for that. Use `intake` for outside PRs only in a VM or container.
6. If you use relay vouching or spec sign-offs, prefer a dedicated SSH key loaded in `ssh-agent` (`PULLBOARD_SSH_KEY`) over your main key file.

## Not covered
- **Thin runtime:** only `--help` and `--version` ran (see the list above). A useful re-run would plant `~/.claude` settings, then in a sample git repo run `pullboard init` (non-interactive), print `.claude/settings.json` and `git config core.hooksPath`, run `fire_hooks.py .claude/settings.json .`, run `pullboard tour`, and start `pullboard view` for ~45 s.
- **Partial code review:** this is a 1,500-file repo (~1,350 JS files, many of them tests). The review covered the network calls, relay key and SSH handling, Keychain, init/hooks/agent hooks, the view server's origin checks, shell-exec sites, the skills and the release workflow. The relay server code (`relay/`, the hosted service) and most command modules were checked only by scanners and greps.
- **Hosted code:** the JavaScript served by app.pullboard.dev and the relay's real deployment were not inspected. The claim that the relay "can't read" your board comes from the project's docs and client code, not an end-to-end check.
- **npm package vs. source:** the published tarball was not compared with this commit (it has provenance, which the audit did not verify).
- **Linux VM ≠ macOS:** the Keychain migration and macOS-only paths (`security`, `sysctl`) were reviewed in code only. Evasion by malware remains possible in general.
- **Unread files:** none (`static/unreadable-by-reviewer.txt` is empty, and no symlinks were stripped).
