# google-research/harness2 — USE WITH PRECAUTIONS
Commit `6868817518876de8fd170c6a8354daca273b6191` (harness2 0.1.0) · audited 2026-11-09 · Google Research framework for "recursive agent harnessing". It runs coding agents (OpenCode by default, Codex optional, or the `claude` CLI as the "improver") on JobBench, LAB and WorkBuddy-Bench tasks. Model-written edits to prompts, scripts, hooks and plugins are fed back into later runs. Python CLIs: `harness2`, `-setup`, `-check`, `-judge`, `-report`, `-demo`, `-bridge`.

**Bottom line:** We found no malware, telemetry, obfuscation, persistence or hidden instructions. The risk is in its design, and the README says so: executor agents run **with shell access, unrestricted network and approvals/sandbox disabled**. For JobBench and LAB they run directly on your machine as your user, working on downloaded benchmark tasks and on harness files that a model rewrote. The optional `claude` improver channel runs `claude --dangerously-skip-permissions`. Run it only inside a VM or dedicated cloud box with a dedicated GCP project, never on your main Mac user. **The VM run only installed the package and printed `--help`.** Setup, the demo and all agent runs were not exercised, so the verdict rests on code review.

## What it can touch
- **Processes:** `git`, `npm`, `bun` (OpenCode from source), `uv`, `docker` (WorkBuddy), `gcloud auth application-default print-access-token`, the `codex` binary (`@openai/codex@0.144.6`), the `claude` CLI (only if you pick the `claude_cli` improver channel), and `litellm` (`harness2-bridge`). All are list-argument calls with no `shell=True`.
- **Files:** its own repo folder: `dependencies/` (cloned benchmarks, tools, `codex/home/config.toml`, `codex/bridge.json` with the bridge key at mode 0600), `runs/` (or `HARNESS2_RUNS_DIR`), and `.env` (read by `config.load_dotenv`). Agents get `/tmp` and per-rollout temp folders. Their bash can reach anything your user can.
- **Agent config:** it does **not** touch `~/.claude`, `~/.codex` or shell startup files. Codex gets its own `CODEX_HOME` under `dependencies/codex/home`. OpenCode gets per-session `XDG_DATA_HOME`/`XDG_STATE_HOME`.
- **Network:** GitHub (4 pinned clones), npm, PyPI/uv, Hugging Face (`JobBench/job-bench` dataset), WorkBuddy dataset URLs (SHA256-checked), Vertex AI (`*aiplatform.googleapis.com`), whatever endpoint you set in `HARNESS2_*_BASE_URL`, and a local LiteLLM proxy (`127.0.0.1`, or `0.0.0.0` if you pass `--host`). Agent web access is unrestricted by design.
- **Credentials:** your gcloud Application Default Credentials (for Vertex), plus optional `HARNESS2_JUDGE_API_KEY`/`HARNESS2_CODEX_API_KEY`. A scrub list strips 20 common secrets (Anthropic, OpenAI, Gemini, GitHub, AWS, Slack, Jira) from subprocess environments (`harness2/config.py:193-226`). It does **not** strip gcloud ADC (`~/.config/gcloud`) or other files, so an agent with bash can still read them.
- **Persistence / auto-run:** none. No pip install hooks, no Claude hooks, no MCP server, no auto-update.

## Runtime behaviour (VM, decoy credentials, network blocked)
- **Install** (auto scenario: `uv venv` + `uv pip install -e .`, no extras): 6 s, exit 0. It contacted only `pypi.org` and `files.pythonhosted.org` through the proxy (the base package has zero dependencies). No refused hosts, no direct egress, 0 decoy reads. The only home reads were uv config probes and the scenario's own `bash` writing the planted `~/.claude` files.
- **Run:** `--help`/`--version` on all 7 console scripts. 2 s, 0 DNS lookups, 0 connections, 0 decoy reads. No processes were left running.
- **Persistence:** none. No startup files, cron, autostart or new executables. The only new files were the two `~/.claude` config files the scenario planted, and they were unchanged.

## How to use it safely
1. **Run it only in a disposable Linux VM or cloud instance** (the README already says Linux only), not as your main Mac user. JobBench and LAB agents run on the host with shell access and no approvals.
2. **Use a dedicated GCP project and service account** with Vertex access only and a budget cap. The agents can read whatever gcloud credentials sit in that machine's home directory.
3. **Restrict egress at the network level** as `docs/EXPERIMENTS.md` ("Web access") recommends: model endpoint, package registries and nothing else during rollouts.
4. Keep the default `opencode` improver channel. Use `claude_cli` only in the same VM, with a Claude login that has nothing else attached.
5. Run `harness2-bridge` on `127.0.0.1` unless WorkBuddy needs `0.0.0.0`. In that case, firewall the port to the Docker bridge.
6. Pin: clone at `6868817`, install in a venv. After `harness2-setup`, record the JobBench dataset revision it wrote (`.harness2-download.json`). Start with `harness2-demo` (local, no credentials) and `--dry-run`.
7. Treat `runs/` as untrusted output: it contains model-written scripts and hooks. Re-audit before updating.

## Not covered
- **Most of the tool did not run.** The auto scenario only installed the base package and printed `--help`. It did **not** install the `[render]` or `[bridge]` extras, and it did not run `harness2-demo` (README step 4, needs no credentials), `harness2-setup jb|lab|wb` (git clones, `bun install`, `uv sync`, Hugging Face download, Docker builds, `npm install @openai/codex`), `harness2-check`, any `harness2` rollout, the judge or report steps, or the bridge. There is no Vertex, Docker, `claude` or Codex in the VM. Agent behaviour, setup downloads and generated-harness execution were reviewed in code only. A useful re-run: install.sh adds `uv pip install -e '.[render]'`, and run.sh runs `harness2-demo --output /home/sandbox/work/demo --k 2` and `harness2-setup jb --dry-run`.
- **Third-party code fetched at setup** (OpenCode, job-bench-eval, harvey-labs, workbuddy-bench at their pinned commits, the bun/npm/uv dependency trees, the Codex binary, the datasets) was not reviewed. Only the patches and overlays shipped in this repo were checked. osv-scanner found no lockfile in this repo.
- **Large surface:** 72 Python files. We reviewed install, config, bridge, proposer, the substrates and the runner launch sites, plus every network/subprocess/env/home-path hit, but not every prompt template.
- **Unread file:** `.env.example`, hidden by your deny rules (the VM scanners covered it; gitleaks found nothing). No symlinks were stripped.
- **Linux VM ≠ macOS** (the tool targets Linux anyway), and evasion by malware remains possible in general.
